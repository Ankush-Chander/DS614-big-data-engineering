Elasticsearch Replication

Elasticsearch Data Replication

Elasticsearch uses a leader-based replication model at the shard level, combined with automatic distribution and failover mechanisms. It is conceptually closest to single-leader replication, but applied per shard rather than per database.

1. Core Abstraction: Index → Shards → Replicas

An index in Elasticsearch is divided into shards, and each shard is replicated.

  • Primary Shard

  • Acts as the leader for that shard

  • Handles all write operations

  • Replica Shard

  • Copies of the primary shard

  • Serve read requests
  • Provide redundancy

Example:

Index: users
Shards: 3 primary shards
Replicas: 1 replica per primary

Total shards = 3 primaries + 3 replicas = 6

Each shard is placed on a different node to ensure fault tolerance.

2. Write Path (Indexing Flow)

Elasticsearch enforces a strict primary-first write model.

Step-by-step flow

  1. Client sends a write request (index/update/delete) to any node
  2. That node acts as a coordinating node
  3. Request is routed to the appropriate primary shard

  4. Primary shard:

  5. Validates and applies the operation

  6. Assigns a sequence number (ordering guarantee)
  7. Primary forwards the operation to all replica shards
  8. Replicas apply the operation in the same order
  9. Acknowledgment is returned

Acknowledgment modes

  • default (quorum-like behavior): success after primary + replicas respond
  • async option: client gets response after primary (faster but riskier)

This is similar to semi-synchronous replication in traditional databases.

3. Read Path

Reads can be served from:

  • Primary shard
  • Any replica shard

This enables horizontal read scaling.

Load balancing

  • Elasticsearch automatically distributes read requests across replicas
  • Improves throughput and latency

4. Consistency Model

Elasticsearch provides near real-time (NRT) consistency, not strict immediate consistency.

Key concepts

  • Refresh interval (default ~1 second)

  • Data becomes searchable only after refresh

  • Writes are durable before they are searchable

  • Translog (transaction log)

  • Ensures durability before data is flushed to disk

  • Sequence numbers + primary terms

  • Ensure correct ordering of operations

  • Prevent stale replicas from overwriting newer data

5. Failure Handling and Failover

Primary shard failure

  1. Cluster detects node failure
  2. One of the replicas is promoted to new primary
  3. Cluster rebalances to maintain replica count

This is analogous to automatic failover in leader-based systems.

Replica failure

  • Missing replica is recreated from primary
  • No write disruption unless replication factor is violated

6. Replication Guarantees

Elasticsearch ensures:

  • Write ordering per shard
  • At-least-once replication
  • No split-brain (via cluster coordination)

Cluster coordination is handled by a consensus mechanism (Zen2, inspired by Raft-like principles).

7. Shard Allocation and Placement

Elasticsearch automatically manages:

  • Shard distribution across nodes
  • Avoids placing primary and replica on same node
  • Rebalances when nodes join/leave

Goals

  • Fault tolerance
  • Even load distribution
  • Efficient resource usage

8. Network and Performance Considerations

Replication cost depends on:

  • Number of replicas
  • Network bandwidth
  • Write rate

Trade-offs:

More Replicas Fewer Replicas
Higher read throughput Faster writes
Better fault tolerance Lower resource usage
Higher network overhead Less redundancy

9. Handling Replication Lag

Unlike async DBs, Elasticsearch minimizes lag by:

  • Applying writes to replicas immediately
  • Using in-sync replica set (ISR)

In-sync replicas

  • Only replicas that are fully caught up
  • Writes are acknowledged only if ISR condition is satisfied

If a replica falls behind:

  • It is removed from ISR
  • Must catch up before rejoining

10. Comparison with Classical Replication Models

Feature Elasticsearch
Model Single-leader (per shard)
Writes Only to primary shard
Reads Primary + replicas
Failover Automatic
Consistency Near real-time
Scaling Horizontal via sharding

11. Key Design Insights

1. Shard-level leadership

Instead of one global leader:

  • Each shard has its own leader
  • Enables massive parallelism

2. Tight integration with storage

  • Replication is tied to Lucene segments
  • Efficient but less flexible than logical replication

3. Built for search, not transactions

  • Optimized for:

  • High read throughput

  • Distributed indexing

  • Not ideal for:

  • Strong transactional guarantees

12. Subtle Failure Scenarios

Lost acknowledged writes (rare but possible)

If:

  • Primary acknowledges
  • Crashes before replicas persist

Mitigation:

  • Use higher replication settings
  • Durable translog configuration

Stale reads

Due to refresh interval:

  • Recently written data may not appear in search immediately

Solution:

  • Force refresh (costly)
  • Use GET (real-time API)

13. Mental Model

Think of Elasticsearch as:

  • A collection of mini leader-follower systems (shards)

  • Each shard:

  • Has one leader (primary)

  • Multiple followers (replicas)
  • Coordinated by a cluster manager
